## R03 の回帰は「減らす」方向で解決した

R03 では data race や取りこぼしを潰すために機構を足したが、R04 でその多くが
**重複か逆効果**だと分かった。同じ問題に 2 つの機構を当てると、両方が成立したときに
新しい不整合（F12 の二重サンプル）が生まれる。

| R03 で足したもの | R04 での判断 |
|---|---|
| 切替直後の回収（R03-F01(b)） | **削除**。定常状態では 1 件も拾えず、publish 後の世代確認と重複していた |
| 手書きの schema 版（R03-F05） | **自動導出に置換**。人が維持する数字を無くした（制約 A） |
| reader のスロットロック（R03-F04） | **維持**。ただし writer 側の探索を全スロットに広げ、待ち方をカーネルに変えた |

## F23 — フレーキーの追跡

R04 の対応中、約 2% の頻度で 1 件だけ落ちる実行があった。原因が分からないまま
進めると「新しい実装の問題か既存の問題か」の判別がつかなくなるため、
先に追跡した。

**再現手順の確立が決め手だった。**

1. `/dev/shm` を mount namespace で分離し、他の作業と干渉せず並行して反復できるようにした
2. 疑わしいテストだけを高速に回した（通常環境では 80 回連続で再現せず）
3. **CPU に 20 スレッドの負荷をかけると 25 回中 16 回失敗した**

落ちていたのは `FailedSubscribeMustNotCorruptPreviousValue` で、publisher が
「could not acquire a writable slot」で例外を投げていた。原因は待ち方で、
`lockSlotWithin()` が `trylock` + `sched_yield` のスピンだったため、CPU が
過負荷のときに待ち手が自分の量子を浪費するだけで保持者に CPU が回らなかった。

`pthread_mutex_clocklock(CLOCK_MONOTONIC)` でカーネルに眠るようにして
**16/25 → 2/25**。残る 2 回は `buffer_num = 1` という構成そのものに由来する
（reader もスロットを排他する以上、スロットが 1 つなら奪い合う）。
production では `buffer_num = 1` を使っている箇所は無く（既定 3、全 7 箇所はテスト）、
ライブラリは黙って壊すのではなく例外で知らせるので契約どおりである。
テスト側の前提を実態に合わせて **0/25** になった。

> ThreadSanitizer は `pthread_mutex_clocklock` を捕捉せず「未ロックの mutex を
> unlock した」と誤検出して 80 件落ちる。TSan ビルドではスピン待ちに切り替える。

## 利用者側コードへの制約（R04 を受けた設計変更）

R04 の指摘 29 件のうち相当数が「利用者が守るべき約束を、ライブラリ側が防御的コードで
肩代わりしている」ことに起因していた。防御コードを足すほど複雑になり次のレビューで
新しい穴が見つかる循環になるため、**約束をコンパイル時か起動時に強制する**方向へ
舵を切った。検討の全文は [`r04-user-facing-constraints.md`](r04-user-facing-constraints.md)。

### 制約 A — 型のレイアウトを自動でハッシュする（実装済み）

```cpp
struct LidarScan { uint32_t count; float ranges[1081]; };
SHM_DECLARE_LAYOUT(LidarScan, count, ranges);
```

`sizeof(T)` / `alignof(T)` と各メンバの `offsetof` / `sizeof` から `constexpr` の
ハッシュを作る。**版番号を維持する判断が無い**のが要点で、並べ替え・型入れ替え・
追加・削除・アライメント変更がすべてハッシュに出る。

メンバの書き漏らしや並べ間違いは**コンパイルエラー**になる
（並べたメンバが型を隙間なく覆っているかを検査する）。唯一検出できないのは、
書き漏らしたメンバが「どのみち必要なパディング」にちょうど収まる場合だけで、
`offsetof` / `sizeof` だけを情報源とする以上これは原理的に区別できない。

ワイヤ形式が `serialize()` の実装で決まる型（cv::Mat / Lidar2dScanData /
PointCloud2DScanData）はレイアウトから導出できないので
`SHM_DECLARE_SERIALIZED_FORMAT(T, revision)` で明示する。

`SHM_REQUIRE_LAYOUT`（**既定 OFF**）を ON にすると未宣言の型がコンパイルエラーになる。
既定 OFF なのは移行のためで、workspace には 90 種類以上のペイロード型があり
一斉に必須化すると複数リポジトリのビルドが同時に止まる。パッケージ単位で ON にして
移行し、全部済んだら既定を ON にする。

### 制約 D — `shm_tool doctor`（実装済み）

`/dev/shm` の全セグメントのヘッダを読み、そのまま使えるかを報告する。
ABI・世代・書式・buf_num に加えて **実際に保持している履歴長**を表示する。

対処が必要なもの（★、終了コード 1）: 未初期化 / 別形式 / ABI 不一致 /
再起動前の残骸 / 名前とヘッダのノンス不一致 / 古い世代の残骸 /
切り替え競争に負けた残骸。「書式が未宣言」は注記に留める（終了コード 0）。

### 制約 B / C（未実装・設計のみ）

トピック定義を一元化し、**発行レートと必要な履歴長**からバッファ数を導出する案。
初版は「想定 reader 数」を宣言させる案だったが、次の理由で撤回した。

- スロットのロックは `memcpy` の間しか保持しないので、1Hz で読む消費者が
  1 秒間スロットを占有することはない。プロセス数を書かせても形骸化する
- スロット枯渇は safety ではなく liveness の問題であり、確率的に十分で構わない

実際に宣言させる価値があるのは**履歴の深さ**だった。10Hz のセンサを `buf_num = 3` で
持つと履歴は 300ms しかなく、1Hz の消費者が 1 秒前のオドメトリに合わせようとしても
届かない。しかも `Nearest` は必ず「最も近いもの」を返すので、これは黙って
間違った答えになる（F14 で `max_skew_us` を必須にして塞いだ）。

## 未実施

- **Raspberry Pi 4（aarch64）での実行**。ビルドは確認済み（2026-09-02）。次の点は実機で確かめる価値がある。
  - `ShmHeader` 192 バイトの `static_assert`（クロスコンパイル + qemu では検証済み）
  - `pthread_mutex_clocklock` の可用性（aarch64 の glibc 版に依存。2.30 未満ならスピンに落ちる）
  - `PTHREAD_PRIO_INHERIT` と SCHED_FIFO の組み合わせ
- **実センサでの通し確認**。ABI が 4 に上がったので、入れ替え前に
  `shm_tool remove` で既存セグメントを消し、そのトピックを使う全プロセスを
  同時に起動し直すこと。対象は `shm_tool doctor` で一覧できる。
- **制約 B / C の実装**（トピック定義の一元化と起動時の突き合わせ）。移行方針を決めてから。
- **`SHM_REQUIRE_LAYOUT` の既定 ON 化**。90 種類以上のペイロード型に
  `SHM_DECLARE_LAYOUT` を付ける作業が先。
- **lidar / point_cloud の `publish` が例外ではなく `std::cerr` で知らせる点**。
  稼働中のセンサデーモンの制御フローが変わるため、実機で確認できる状況で扱う。
